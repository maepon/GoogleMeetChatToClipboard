# AI開発フロー 導入・運用ガイド

> このガイドは、`Makefile` / `scripts/` / `prompts/` / `.claude/` の一式（AI開発フロー）と一緒に配布される
> 導入・運用の説明書です。単体で完結しているので、これだけ読めばセットアップと日々の運用ができます。

## 0. このリポジトリでの調整

このリポジトリ（GoogleMeetChatToClipboard）に移植した時点での、標準構成からの変更点です。

- **自動テスト・フォーマッタ未導入。** `npm test` は無く、Prettier 等のフォーマッタも
  入っていないため、`scripts/run-phase.sh` の整形チェックは `format_target()` を常に偽にして
  無効化してあります。動作確認はすべて `tmp/` 配下のスクリプトから `node` で
  `modules/` 配下の関数を直接呼び出す方法に統一しています（`.claude/*-permissions.json` の
  allow は `Bash(node tmp/:*)` のみ）。テストランナーやフォーマッタを導入したら、
  `scripts/run-phase.sh` の `format_target()` / `format_ok()` / `FORMAT_FIX` と、
  各プロンプトの `node tmp/<ファイル名>.js` の案内をそちらに書き戻してください
- **`docs/` を案件のドキュメント（`docs/development/` など）に使っている**ため、
  `TOOLING_PATHS` は `docs/` 全体ではなく `docs/ai-workflow-setup.md`（このファイル）だけを
  保護対象にしてあります。`docs/development/` 配下はエージェントが自由に更新できます
- **CI設定（`.github/workflows/`）を保護対象に含めています。** エージェントは CI 設定を
  変更できません。CI の変更は人が別コミットで行ってください
- **Slack Incoming Webhook は未設定です。** `.env` に `SLACK_WEBHOOK_URL` を設定するまで
  `make spec` / `make impl` などは最初の `check-env` で止まります（§2「Slack」参照）
- **`.claude/` の扱い。** このリポジトリはもともと `.gitignore` で `.claude/` を丸ごと
  除外していました。`.claude/*-permissions.json` をコミットできるよう、
  `.claude/settings.json` と `.claude/settings.local.json` だけを除外する形に変更しています

## 1. これは何か

**GitHub Issue を起点に、Claude Code をヘッドレスで回して Pull Request まで持っていく仕組み**です。
`make spec` で仕様を固め、`make impl` で実装・レビュー・PR 作成まで進みます。

```
Issue
 │
 ├─ make spec ────► 質問状 または 指示書（受入基準つき）を Issue に投稿して停止
 │                   ▲
 │                   └─ 人が読む ← ここが唯一の人間ゲート
 │
 └─ make impl ────► 計画書 → 判定 → 改訂（承認まで最大3周）
                     → 実装
                     → レビュー → 修正（承認まで最大3周）
                     → コミットして PR 作成
                     → PR へコードレビューを投稿
                                    ▲
                                    └─ 人がマージを決める
```

設計の芯は3つです。

1. **人間ゲートは1箇所だけ。** 指示書の確認だけを人がやり、そこから PR までは止まりません。
   ゲートを増やすと自動化の意味が薄れ、減らすと仕様が固まらないまま実装が走ります。
2. **判定は受入基準の項番だけで決める。** `AC-1`, `AC-2`, … との対応でのみ合否を出します。
   印象で判定させると収束しません。
3. **収束しなかったら止めて人に投げる。** 最大3周してだめなら Slack に通知して停止します。
   自動で先に進めるとレビューが形式だけになります。

**経緯はすべて Issue のコメントに残ります。** ローカルの `tmp/` は作業用で、消えても Issue から再開できます。

## 2. 前提

### コマンド

| コマンド | 用途 | 確認 |
|---|---|---|
| `claude` | Claude Code CLI。ヘッドレス実行（`claude -p`）を使う | `claude --version` |
| `gh` | GitHub CLI。Issue の読み書き、PR 作成 | `gh auth status` |
| `jq` | Claude の JSON 出力を読む | `jq --version` |
| `curl` | Slack 通知 | `curl --version` |
| `make` | 入口 | `make --version` |
| `bash` | スクリプトの実行 | `bash --version` |

### bash のバージョンについて

スクリプトは **macOS 同梱の bash 3.2 で動くように書いてあります。** 連想配列や `${x^^}` のような
4.x の機能は使っていません。移植先で bash 4/5 を使うのは問題ありませんが、3.2 互換のまま保つと
どの環境でも動きます。

3.2 には**変数名のパースがマルチバイト非対応**という落とし穴があります。`$x` の直後に非 ASCII 文字が来ると、
その文字の先頭バイトを変数名に取り込み、`set -u` と組み合わさって `unbound variable` で落ちます。

```bash
fail "ブランチ名が feature/ で始まっていません（$branch）"   # ✗ 落ちる
fail "ブランチ名が feature/ で始まっていません（${branch}）" # ✓
```

**これはエラーメッセージの中で起きるので、普段は動いていて失敗したときだけ落ちます。**
`scripts/check-scripts.sh` がこの形を静的に検出するので、フェーズの前に必ず通ります。

### GitHub

- リポジトリが GitHub にあり、`gh` が認証済みであること
- **Issue を使う運用であること。** このフローは状態を Issue コメントに持ちます
- 既定ブランチ（PR のベース）の名前を `Makefile` の `BASE_BRANCH`（既定 `main`）と合わせておくこと

### Slack

Incoming Webhook の URL が必要です。**未設定だと `make` が最初に止まります**（意図的な作りです。
長時間走るフェーズの結果を人が取りこぼさないため）。

Slack を使わないなら `scripts/notify-slack.sh` を「何もせず終了コード0で返す」に差し替えてください。
`Makefile` の `check-env` から `SLACK_WEBHOOK_URL` の検査も外します。

### モデル

使うモデルは**2ティア**です。判断と突き合わせを担う**強モデル**（`STRONG_MODEL`）と、
量のある作業を担う**高速モデル**（`FAST_MODEL`）。`Makefile` の2行が既定値を環境変数から取ります。

```sh
export CLAUDE_CODE_OPUS_MODEL=<強モデルのID>
export CLAUDE_CODE_SONNET_MODEL=<高速モデルのID>
```

参照する環境変数名を変えたいときは `Makefile` の該当2行だけを直します。
環境変数を定義していないなら、`.env` に直接書いても効きます（`.env.example` にコメントアウトした行があります）。

```make
STRONG_MODEL = <強モデルのID>
FAST_MODEL = <高速モデルのID>
```

`?=` ではなく `=` で書いてください。`Makefile` 側で先に定義済みなので、`?=` だと値が入りません。

役割分担は次のとおりです。

| 役 | ティア | 理由 |
|---|---|---|
| 指示書の作成、計画の判定、実装のレビュー判定、PR 本文、コードレビュー | 強モデル | 判断と突き合わせが仕事 |
| 計画書の作成、計画の改訂、実装、指摘の修正 | 高速モデル | 作業量が多く、指示が具体的 |

**変数名を製品名にしていないのは、どのフェーズにどちらを割り当てるかが `scripts/run-phase.sh` 側の方針で、
実際に入れ替えて試すもの**だからです（`REVIEW_JUDGE_MODEL`、§4）。実行時に使ったモデルIDは
ステップごとに stderr に出るので、ログではどちらで回したかが分かります。

> **`.zshrc` に書いた環境変数は非対話シェルから読まれません。** ターミナルから `make` を打つぶんには
> 引き継がれますが、Claude Code の Bash ツールや IDE のタスクなど、非対話のシェルから `make` を呼ぶと未設定扱いになります。
> どこから呼んでも効くようにするなら、`.zshenv` に置くか `.env` に書いてください。

### `.gitignore`

以下が必要です。

```
.env
.claude/settings.json
.claude/settings.local.json
tmp/
```

**`tmp/` は必須です。** エージェントがコメント本文を書き出す場所で、git 管理下にあると
`run-phase.sh` の作業ツリー検査が毎回発火してフローが止まります。

## 4. 使い方

| コマンド | 中身 | 終わり方 |
|---|---|---|
| `make spec ISSUE=n` | 強モデルが Issue とコードを読み、**質問状** または **指示書** を投稿 | 止まる（人が読む） |
| `make impl ISSUE=n` | 計画書 → 判定 → 改訂 → 実装 → レビュー → 修正 → コミットして PR 作成 → コードレビュー | PR ができる |
| `make review ISSUE=n` | `impl` の後半（レビュー以降）だけを回す | PR ができる |
| `make code-review ISSUE=n` | PR への純粋なコードレビューだけを回す | PR にコメントが付く |
| `make pr-review ISSUE=n` | PR への反論レビュー（Devil's Advocate）。メインフローからは外してある | PR にコメントが付く |
| `make check` | 静的検査だけを走らせる（各フェーズの前に自動で通る） | — |

`review` を単独で叩くのは、`impl` が収束せずに止まったあと、手で直して再開するときです。
`code-review` 単独は、PR はできたのに投稿だけ失敗したときの入口です。

変数: `ISSUE`（対象Issue番号）、`MAX_ROUNDS`（判定の最大周回数、既定3）、`BASE_BRANCH`（PR のベースブランチ、既定 `main`）、
`REVIEW_JUDGE_MODEL`（実装レビューの判定モデル。`strong` / `fast` か生のモデルIDを受ける。未設定なら強モデル）。

実装レビューの判定だけ高速モデルで足りるかを試せます（`make impl ISSUE=n REVIEW_JUDGE_MODEL=fast`）。
計画の判定は文章同士の突き合わせで実行による裏取りができないため、強モデル固定にしてあります。

### 人が介入する1箇所

**指示書の確認だけです。**

- **質問状が来たら** — Issue にコメントで答えて `make spec ISSUE=n` を再実行
- **指示書に直したいところがあれば** — 同じく Issue にコメントして `make spec ISSUE=n` を再実行
- **指示書が無いまま `make impl` を叩くと止まります**

再実行したとき、spec は指摘を取り込んだ**指示書の全文**を投稿し直します。下流のフェーズは
**最新の** `INSTRUCTION` だけを仕様の正として読むので、古い指示書は自動的に無効になります。
**差分だけをコメントしても仕様にはなりません。**

### Issue コメントの種別（AI-TAG）

コメントの先頭の `<!-- AI-TAG: … -->` で種別が分かります。

| タグ | 出す役 | 中身 |
|---|---|---|
| `QUESTION` | spec | 仕様を決めるための質問状 |
| `INSTRUCTION` | spec | 指示書。**受入基準（`AC-n`）を含む。下流はこれだけを仕様として読む** |
| `PLAN` | plan | 実装計画書とテストシナリオ |
| `PLAN_REVIEW` | plan-judge | 指示書との齟齬の判定 |
| `IMPLEMENTATION_DONE` | implement | 実装の報告 |
| `CRITIC_REVIEW` | review-judge | 受入基準に対する合否の判定 |
| `RESIDUAL_RISK` | review-judge | 受入基準の外に残った危なさ（**判定には影響しない**） |
| `FIX` | review-fix | 指摘の修正内容 |
| `CODE_REVIEW` | code-review | **PR に付く。** 受入基準を離れたコードレビュー（判定に影響しない） |
| `DEVILS_ADVOCATE` | pr-review | **PR に付く。** 受入基準そのものへの反論（判定に影響しない） |

### Issue の書き方

指示書の質はそのまま実装の質になり、**受入基準の曖昧さはそのまま収束しない原因になります。**

- **Issue には「何をしたいか」と「なぜ」を書く。「どうやるか」は書かなくてよい** — 手段は計画書で決まります
- **1 Issue の大きさは目的の数で測る。** ファイル数やステップ数ではありません。目的が2つあるなら2 Issue に割ります
- 前提が曖昧なまま `make spec` を叩いてよい。質問状が返ってくるので、そこで答えれば済みます

## 5. 判定の設計

### なぜ受入基準の項番だけで判定するのか

判定役（`plan-judge` / `review-judge`）は、指示書の `AC-1`, `AC-2`, … との対応だけで合否を出します。
「コードの品質が低い」「もっと良い書き方がある」では差し戻せません。

**印象で判定させると収束しないからです。** 差し戻す理由が無限に作れると、3周しても終わりません。
逆に、この設計には避けられない穴があります。

> **レビュアーは受入基準に無い欠陥を止められません。**

受入基準が曖昧だと3周しても収束せず、人待ちで止まります。そのときは**実装ではなく指示書を直してください。**

### 承認を覆せない出力先

上の穴を埋めるために、**判定に影響しない**出力先を3つ用意しています。
判定に影響させないのが要点で、承認を覆せるようにすると判定が印象に戻り、収束しなくなります。
ここで拾った危なさは**次サイクルの Issue の種**として扱います。

| | どこに出るか | 持ち場 |
|---|---|---|
| `RESIDUAL_RISK` | Issue（承認したレビュアーが判定とは別コメントで） | **受入基準の外に残った危なさ**。`AC-n` ごとにどう確かめたか（`実行して確認` / `テストを読んだ` / `コードを読んで推論のみ`）と、事故カタログの巡回結果 |
| `CODE_REVIEW` | PR（`make impl` の最後に別プロセスで） | **受入基準を離れて、コードとして正しいか**。境界条件と型の取り違え、エラーの握りつぶし、セキュリティ（パス操作・TOCTOU・無検証の外部入力）、正常な入力で想定外のエラーになる経路の4観点。読みにくさや書き方の好みは書かせず、「壊れる」「エラーになる」と言える根拠があるものだけ |
| `DEVILS_ADVOCATE` | PR（人が `make pr-review` を叩いたときだけ） | **受入基準そのものの誤り**。「AC を全部満たしても目的が達成されていない」「テストが仕様ではなく実装を追認しているだけ」「今まで通っていた操作が通らなくなる」「入れないほうがよかった」「PR 本文が差分と食い違う」の5つを1件ずつ検討し、成り立たなかったものも成り立たなかったと書かせる |

`CODE_REVIEW` を独立したフェーズにしてあるのは、判定役が受入基準の項番だけで判定する作りのため、
**AC に書かれていない欠陥は構造的に拾えない**からです。

`DEVILS_ADVOCATE` は「AC そのものを疑う」持ち場でこれとは別ですが、**1周あたりのコストが最も大きい
単一ステップ**になりやすいため、既定ではメインフローから外して単独実行に回してあります。

### `RESIDUAL_RISK` の事故カタログ

`prompts/review-judge.md` の後半に、巡回すべき事故パターンのリストがあります。
**このリストは実際に起きた事故から作るものです。** 汎用の項目だけにすると
「特にありません」しか返らなくなるので、**自分のリポジトリで事故が起きたら追記してください。**

### `pr-review`（Devil's Advocate）の主張2

「テストが仕様ではなく実装を追認しているだけではないか」を確かめるとき、
**実装を1行わざと壊してテストが落ちるかを実際に見ます。** 落ちなければ、そのテストはその振る舞いを
検証していません。壊した箇所は元に戻す決まりなので、このフェーズだけ `git restore` を許可した
専用プロファイル（`.claude/pr-review-permissions.json`）を渡しています。
PR 作成後に走るので差分はコミット済みで、restore で失われるものがありません。

戻し忘れは `scripts/run-phase.sh` が**作業ツリーの前後比較**で捕まえます。
`code-review` も同じ前後比較を通します。あちらはコードを直さない決まりですが、
`Write` / `Edit` はパスを絞れずに渡っているので、決まりだけでは担保にならないためです。

## 6. 権限の設計

エージェントに渡す権限は `.claude/` のプロファイルで決めています。

| ファイル | 使うフェーズ | 特徴 |
|---|---|---|
| `.claude/phase-permissions.json` | spec / impl / review | ベース。`gh issue comment` を渡す |
| `.claude/commit-permissions.json` | PR 作成 | `git add` / `git commit` / `git switch` を足す。コミット前の確認用にテストと整形チェック（`npm test` / `npx prettier`）だけ残す |
| `.claude/pr-review-permissions.json` | code-review / pr-review | ベースとの違いは2つ。`git restore` を足し、`gh issue comment` を外す（投稿先は PR なので Issue に書かせない） |

### 実測でわかっている落とし穴

ここは直感に反するので、**プロファイルを編集する前に必ず読んでください。**
詳細は `scripts/claude-run.sh` の冒頭コメントにも残してあります。

**これは Claude Code の仕様ではなく、ある時点のバージョンでの実測です。** 実測した時点のバージョンは記録していません。
最後にこの表と照らし合わせたのは 2.1.243（2026-09-24）です。バージョンが上がれば変わりうるので、
導入時に `claude --version` を控えておき、上がったら次の2点だけでも確かめ直してください。
どちらも高速モデルで短い1回を走らせれば済み、コストは小さく済みます（課金なしでは確かめられません）。

- `Write(tmp/**)` だけを allow したプロファイルで「`tmp/x.txt` に1行書いて」と頼み、拒否されるか
  （通るようになっていれば、書き込み範囲を権限で絞れるようになったということ）
- `.claude/settings.json` という名前のプロファイルを `--settings` で渡し、allow が効くか

| 挙動 | 意味すること |
|---|---|
| `.claude/settings.json` という**名前**だと、`--settings` で明示的に渡しても workspace が trust されていないとき `permissions.allow` が丸ごと無視される（警告は stderr に出るだけで終了コードは0） | **この名前を使わない。** 黙って無権限になる |
| 既定パス以外のファイル名なら allow も deny も効く | プロファイルを `*-permissions.json` にしている理由 |
| `deny` を `settings.json` に置くと**人間の対話セッションまで縛られる**（deny は承認プロンプトを出さずにブロックする） | 自分で commit / push できなくなる |
| `Write` / `Edit` に**パスを付けたルールは allow も deny も一切マッチしない**（`Write(./**)` `Write(**)` `Write(tmp/**)` 絶対パス形すべて拒否された） | 裸の `Write` / `Edit` を渡すしかない。**書き込み範囲の制限はシェル側の作業ツリー検査で行う** |
| `Read` はパス指定が効く。`deny Read(./.env)` は裸の `allow Read` にも勝つ | `.env` は塞げる |
| コロン形の deny は**前置一致**で、ベースコマンドの allow にも勝つ | `Bash(gh pr:*)` の deny が `gh pr comment` も `gh pr create` も塞ぐ |
| Claude Code 自身が `.claude/` 配下への書き込みを塞ぐ | エージェントが自分の権限を広げられない。ただし `prompts/` や `scripts/` は素通りする |
| deny によるブロックは `permission_denials` に**出ず**、ツールのエラーとして返る | 拒否の一覧に出ないものがある |
| ツール呼び出しが拒否されても `claude` の終了コードは **0** | `claude-run.sh` が `permission_denials` を読んで stderr に出している |

### 通してはいけない allow

`scripts/check-scripts.sh` が静的に落とします。

- **`grep` / `cat` / `sed` / `awk` / `head` / `tail` / `cp` / `mv` / `chmod` / `curl` / `ln` / `tee` / `xargs` / `find`** —
  ファイルを読める汎用コマンドを1つ通すと `Read(./.env)` の deny を素通りできます。
  エージェントは `grep` へのパイプを試して拒否されますが、それは想定どおりです（`Read` で代替させます）
- **`git -C <path>` / `<コマンド> -C <path>`** — Bash のマッチは前置文字列なので、
  `git -C . push` が `git push` の deny をすり抜けます
- **1コマンドで何でも走る形のシェルとインタプリタ** — `bash` / `sh` / `zsh` / `env` / `eval` / `exec`、
  裸の `python` / `node` / `npx` など、一行実行の `-c` / `-e` / `-p`、後ろが空の `python -m:*`
  （`python -m http.server` も通る）。`python -m pytest:*` や `npx prettier:*` のように**何を走らせるかまで絞れば通ります。**
  `npm run:*` は検査では落ちませんが、同じ理由で `npm run lint:*` のようにスクリプト名まで書いてください
- **`Bash(git:` / `Bash(gh:` / `Bash(*` / `Bash(:`** — 広すぎる形

### 全プロファイルに必須の deny

1つでも欠けると `make check` が落ち、フェーズが始まりません。

```
Read(./.env)
Bash(git push)
Bash(git push:*)
Bash(gh pr:*)
Bash(rm:*)
Bash(git rebase:*)
Bash(git reset --hard:*)
```

### deny は「隔離」ではない

**テスト実行を許可している以上、エージェントは任意のコードを実行できます。**
その気になれば deny した操作にも到達します。権限リストは事故の防止であって、サンドボックスではありません。

実効的な防波堤は次の3つで、**移植先でもこの3つを外さないでください。**

1. **`.claude/` への書き込みは Claude Code 自身が塞ぐ** — 自分の権限を広げられない
2. **`scripts/run-phase.sh` が各ステップ後に作業ツリーを見て、基盤ファイルの改変で中断する**
3. **`push` と `gh pr` はそもそも渡さず、`run-phase.sh` が検査してから実行する** —
   ブランチ名の規約と、基盤ファイルが案件のコミットに混ざっていないことを機械的に確認します。
   危険な push の形を権限ルールの列挙で塞ぐのは漏れるので、渡さないことにしています

したがって、**エージェントに渡す環境変数にシークレットを残さないこと。**
`Makefile` が `SLACK_WEBHOOK_URL` を export しているので、`claude-run.sh` は `env -u` で外しています
（外さないと `echo` で読めて `Read(./.env)` の deny が無意味になります）。

### 基盤ファイルの保護

`run-phase.sh` は各ステップの後に作業ツリーを見て、**基盤ファイル**（`Makefile` / `scripts/` / `prompts/` /
`.claude/` / `docs/ai-workflow-setup.md` / `.gitignore` / `.env.example` / `.github/`）が書き換わっていたら中断します。
`Write` / `Edit` にパスを付けられないので、これが唯一の担保です。

対象は `run-phase.sh` の `TOOLING_PATHS` で決まります。エージェントに見せる同じ一覧が
`prompts/_rules.md` と `prompts/pr.md` にあるので、変えるときは3箇所をそろえます。**このリポジトリは
`docs/` を案件のドキュメント（`docs/development/` 等）にも使っているため、`docs/` 全体ではなく
このガイド（`docs/ai-workflow-setup.md`）だけをファイル単位で保護対象にしてあります**（§0 参照）。
`.github/workflows/` の CI 設定も保護対象に含めています。

同じ検査で、作業ツリーに出ているソースがフォーマッタに通っているかも見ます（未整形なら中断）。
**整形はシェルではせず、エージェントに掛けさせます。** シェルが差分を書き換えると、
レビュアーが読んだ内容と実際の差分が食い違うためです。

> **フェーズが走っている間は基盤ファイルを触らないでください。**
> この検査は人の編集をエージェントの仕業として中断します。止まっても成果物は残っているので、
> `make review` などで再開できます。

### コミットの分け方

**基盤ファイル**（上の `TOOLING_PATHS` の対象）は**人が既定ブランチに直接**入れます。
**案件の変更**は `feature/` ブランチに載せて PR にします。**この2つを1つのコミットに混ぜません。**

`run-phase.sh` が PR 作成の直前に検査し、混ざっていたら PR を作らずに中断します。

```
  pr-body-issue<N>.md                PR の本文
```

### プロンプトの仕組み

`claude-run.sh` が各プロンプトに `prompts/_rules.md` を**連結**し、プレースホルダを埋めて渡します。

| プレースホルダ | 中身 |
|---|---|
| `{{ISSUE}}` | Issue 番号 |
| `{{VERDICT_FILE}}` | 判定の1語を書き込むファイル |
| `{{COMMENT_FILE}}` | コメント本文を書き込むファイル（プロンプト名から自動で決まる） |
| `{{PR_TITLE_FILE}}` / `{{PR_BODY_FILE}}` | PR のタイトルと本文 |
| `{{BASE_BRANCH}}` | PR のベースブランチ（`Makefile` の `BASE_BRANCH`）。差分を読むときの `origin/{{BASE_BRANCH}}..HEAD` など |

**判定を求められたフェーズは `{{VERDICT_FILE}}` に指定された1語だけを書きます。**
説明文や飾りが混ざると、`make` が次に進めず人待ちで止まります。

### プロンプトを書き換えるときの注意

- **`prompts/_rules.md` は全フェーズに効きます。** ここへの追記は全フェーズのコストに乗ります
- **エージェントは1回の呼び出しで1コマンドしか打てません。** 複合コマンド（`cd X && cmd`、`cmd1; cmd2`、
  制御構文、`VAR=値 cmd` の前置、コマンド置換、パイプ、ヒアドキュメント）は**許可済みのコマンドでも拒否されます。**
  `cd` は許可済みで、カレントディレクトリは呼び出しをまたいで持続するので2回に分けて打たせます。
  この案内が `_rules.md` に無いと、エージェントが拒否され続けて空回りします
- **`cp` は許可していません**（`cp ./.env /tmp/x` で `Read(./.env)` の deny を迂回できるため）。
  テスト用の入力ファイルは `Write` ツールで作らせます

## 8. 止まったときの読み方

終わり方は3通りです。

| 終わり方 | 終了コード | Slack | 意味 |
|---|---|---|---|
| 完走 | 0 | 結果の通知 | 次のステップへ |
| `halt`（人待ち） | **0** | `:raising_hand:` | 失敗ではない。人が読んで判断する |
| `fail`（中断） | 1 | `:x: *<フェーズ> 中断*` | 想定外。メッセージに再開方法が書いてある |

`halt` の終了コードが 0 なのは、**人待ちは失敗ではない**からです。CI に組み込むときはここに注意してください。

### 中断メッセージには再開方法が書いてあります

`fail` のメッセージは「何が起きたか」と「どう直して、どのコマンドで再開するか」を含む形で書いてあります。
**成果物は消えません。** 作業ツリーの実装も、Issue のコメントも残っています。

よく出るもの:

| メッセージ | 原因と対処 |
|---|---|
| `Issue #n に指示書がありません` | `make spec` を先に。人間ゲート。**指示書があるのに出る場合**は `gh issue view --comments` の出力が大きくなったことによる `require_instruction`（`run-phase.sh`）内の SIGPIPE 競合を疑う。`gh` の出力を直接 `grep -q` にパイプすると、コメントが増えて出力が大きいときに `grep -q` が早期終了して `gh` が SIGPIPE（終了コード141）を受け、`pipefail` の下でマッチ済みでも失敗扱いになることがある。一時ファイル経由に直せば起きない（実測でハマった） |
| `判定ファイルの内容が想定外です: '…'` | エージェントが判定の1語以外を書いた。Issue のコメントを読んで判断 |
| `… が基盤ファイルを書き換えました` | `git` で戻してから再実行。**フェーズ中に人が触った場合もこれになります** |
| `… が整形チェックを通らないファイルを残しました` | フォーマッタを掛けてから `make review` で再開。整形済みなのに出るなら、フォーマッタが入っていないか構文エラー（チェック自体の失敗も止める側に倒してある） |
| `ブランチ名が feature/ で始まっていません` | 規約。エージェントの実装は残っているのでブランチを切り直す |
| `案件のコミットに基盤ファイルが混ざっています` | 別コミットに分ける |
| `origin/… が見つかりません` | `Makefile` の `BASE_BRANCH` が既定ブランチと合っていない。直して `make review` で再開 |
| `origin/… と差がありません` | エージェントがコミットしていない。`make review` で再開 |
| `PR が見つかりません` | `code-review` / `pr-review` を単独で叩いたとき、現在のブランチに PR が無い |
| `MAX_ROUNDS 周しても…承認されませんでした` | **受入基準が曖昧なときにこうなります。** 指示書を見直す |

### コストの見方

`tmp/cost-issue<N>.txt` に**追記**されます。`# <日時> <フェーズ>` の見出し行で実行の切り替わりが読めます。

```
# 2026-09-18 20:02:19 spec
2.8436212500000004
# 2026-09-18 20:33:53 impl
0.91197435
...
```

Slack の通知に出る「累計コスト」はこのファイルの合計です。**追記にしているのは、
1周を `make impl` → `make review` と分けて回したときに前半の記録が消えないようにするため**です。

### フェーズが落ちた理由が分からないとき

`claude` の transcript が `~/.claude/projects/<リポジトリパスのスラッグ>/*.jsonl` に残っています。
末尾を読むと、エージェントが何を試して何に拒否されたかが分かります。**課金は発生しません。**

### 権限拒否の警告

```
警告: 許可されていないツール呼び出しが 3 件拒否されました。
  拒否: Bash — cd pkg && npm test
```

**拒否は失敗とは限りません。** エージェントが別手段で回避して完遂する場合があるので停止させず、
人が気付けるように出しています。**繰り返し出るものだけ** プロファイルの `permissions.allow` に足してください
（ただし §6 の「通してはいけない allow」は守ること）。

上の例のような複合コマンドの拒否は、**権限ではなく `prompts/_rules.md` の案内不足**が原因です。

## 9. 導入時チェックリスト

自分のリポジトリに合わせて確認・書き換える箇所です。

### 必ず直すもの

- [ ] **`.gitignore`** に `tmp/` / `.env` / `.claude/settings.json` / `.claude/settings.local.json`
- [ ] **`.env`** を作って `SLACK_WEBHOOK_URL` を設定
- [ ] **環境変数** 強モデルと高速モデルのID（既定の参照元は `CLAUDE_CODE_OPUS_MODEL` /
      `CLAUDE_CODE_SONNET_MODEL`。`.zshrc` ではなく `.zshenv` か `.env` に置く）
- [ ] **`scripts/run-phase.sh` の整形チェック**（`format_target()` / `format_ok()` / `FORMAT_FIX` の3つだけ） —
      対象拡張子と、フォーマッタのチェックコマンド。`format_ok()` は**整形済みなら真を返す**。
      `gofmt -l` のように出力で答えるツールは出力が空かを見て、成功時も何か出すツールは出力を捨てて終了コードを使う。
      **整形はしない**（チェックのみ）。**チェック自体が失敗したら偽を返す**
- [ ] **`scripts/run-phase.sh` の `TOOLING_PATHS`** と **`prompts/_rules.md` / `prompts/pr.md` の基盤ファイル一覧** —
      自分のリポジトリの基盤ファイル。CI 設定を含めるかを決める。3箇所をそろえる。
      **`docs/` を案件のドキュメントに使うなら3箇所すべてから外す**（このガイドの置き場所を別に決める）
- [ ] **`Makefile` の `BASE_BRANCH`**（PR のベースブランチ）。スクリプトとプロンプトはこの値だけを使う。
      直書きの `origin/<ブランチ名>` や `--base <ブランチ名>` を足すと `make check` が落ちる
- [ ] **`scripts/run-phase.sh` のブランチ規約**（`create_pr` の `feature/*` の検査）
- [ ] **`prompts/pr.md` のブランチ名** — 上と**必ずセットで**直す。片方だけだと
      エージェントがコミットまで終えた後に PR 作成で中断する
- [ ] **`.claude/*-permissions.json` の allow** — ビルド・テスト・整形コマンド。
      `which` で確認した**絶対パス形も入れる**（エージェントが絶対パスで呼ぶことがある）
- [ ] **`prompts/implement.md` / `review-fix.md` / `review-judge.md` / `pr-review.md` のテストコマンド** —
      **テスト結果をキャッシュするツールなら、無効にする指定を付ける**（Go の `-count=1`、Gradle の `--rerun-tasks`、
      Turborepo の `--force`、Nx の `--skip-nx-cache`、Bazel の `--nocache_test_results`）。
      判定役は自分でテストを走らせて裏を取る建てなので、前回の成功が再生されると効かなくなる。
      pytest や Jest はもともと結果を再生しないので、何も足さなくてよい
- [ ] **`prompts/code-review.md` / `review-judge.md` / `pr-review.md` の実行方法** —
      成果物を動かして確かめる経路。パス結合API名も言語に合わせる
- [ ] **`prompts/_rules.md` の後半** — モノレポ構成の案内と、自分のリポジトリの規約。
      複合コマンド不可と `cd` の持続の2点は**残す**
- [ ] **`prompts/*.md` が参照するドキュメント名**（規約ファイル、README 等）

### 埋めていくもの

- [ ] **`prompts/review-judge.md` の事故カタログ** — 汎用の項目だけだと
      `RESIDUAL_RISK` が「特にありません」しか返さない。自分のリポジトリで事故が起きたら追記する
- [ ] **`prompts/spec.md` / `pr-review.md` の事故例** — 「受入基準に忠実であることは、事故を防ぐことと
      同じではない」を裏づける実例。**自分のリポジトリの Issue 番号が1件入ると目に見えて効くようになる**
- [ ] **「消えると困る成果物」の保護** — `prompts/code-review.md` / `review-judge.md` / `pr-review.md`。
      該当するものが無ければ「実行して確かめるのは `tmp/` の下だけ」だけ残す

### 最初の1周

最初に回す Issue は**1ファイルの小さな修正**くらいが適当です。見るのは実装の質ではなく次の3点です。

1. `make spec` が**指示書**を出すか。質問状ばかり返るなら Issue の書き方か `prompts/spec.md` の調整が必要
2. `make impl` が計画の判定を**1〜2周で**抜けるか。3周で止まるなら受入基準が曖昧
3. 権限拒否の警告に**繰り返し出るコマンド**が無いか

**権限の allow は1周回すと足すべきものが分かります。** 先に完璧を目指すより、
拒否の警告を見て足すほうが早く、余分な許可も増えません。

## 10. 変えてはいけない設計

「簡単にできそう」と削られがちで、削ると**静かに**効かなくなるものです。

| 設計 | 削ると何が起きるか |
|---|---|
| **人間ゲートは spec の後1箇所だけ** | 増やすと自動化の意味が薄れ、減らすと仕様が固まらないまま実装が走る |
| **指示書タグは行頭アンカー（`'^<!-- AI-TAG: INSTRUCTION -->'`）で探す** | 部分一致にすると「指示書（AI-TAG: INSTRUCTION）がありません」と書いた人のコメントや、このフローについて論じたコメントでゲートが通る。**この文章自身がその形をしている。** `check-scripts.sh` が両側（プロンプトとシェル）の一致を検査している |
| **判定は受入基準の項番だけで決める** | 印象を混ぜると3周しても収束しない |
| **収束しなかったら止めて人に投げる** | 自動で先に進めるとレビューが形式だけになる |
| **`RESIDUAL_RISK` / `CODE_REVIEW` / `DEVILS_ADVOCATE` は判定に影響しない** | 承認を覆せるようにすると、書き手が遠慮して書かなくなる |
| **`push` と `gh pr` はエージェントに渡さない** | 危険な push の形を権限ルールの列挙で塞ぐのは漏れる |
| **各ステップ後に作業ツリーを検査する** | `Write` / `Edit` はパスを絞れないので、これが唯一の担保 |
| **git の出力するパスは `-z` で読む**（`run-phase.sh` の `worktree_paths` と `create_pr`） | 普通の `--porcelain` / `--name-only` は日本語やスペースを含むパスを `"…"` でクォートするので、`TOOLING_PATHS` の `^` に当たらない。基盤ファイルの改変も、案件のコミットへの混入も**黙って通る** |
| **整形はエージェントにさせる。シェルは検査だけ** | シェルが差分を書き換えると、レビュアーが読んだ内容と実際の差分が食い違う |
| **整形チェック自体が失敗したら止める**（`format_ok()` は失敗時に偽） | 出力が空かだけで判定すると、フォーマッタが入っていない・構文エラーで何も出さずに落ちたときに「整形済み」になり、**黙って全部通る** |
| **コストログは追記する** | 起動ごとに切り詰めると `make impl` → `make review` で前半の記録が消え、通知の累計が実際より小さく出る |
| **`SLACK_WEBHOOK_URL` を `env -u` で外す** | `Makefile` が export しているので、外さないと `echo` で読めて `Read(./.env)` の deny が無意味になる |
| **エラーメッセージ中の変数は `${x}` と書く** | bash 3.2 が非 ASCII の先頭バイトを変数名に取り込む。**エラー文の中で起きるので、失敗したときだけ落ちる**（`check-scripts.sh` が静的検査している） |
| **権限ファイルを `settings.json` という名前にしない** | workspace が trust されていないと `permissions.allow` が黙って無視され、`deny` が人間の対話セッションまで縛る |
| **`grep` / `cat` / `sed` / `cp` / `git -C` を allow しない** | `grep` / `cat` / `sed` / `cp` はファイルを読めるので `Read(./.env)` の deny を素通りし、`git -C` は前置一致をずらして `git push` の deny を迂回する |
